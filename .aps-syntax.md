# Agile Protocol Specification Syntax

**Candidate syntax coordinate:** APS v26.7.31  
**Canonical edition source:** `specification-guide/src/`  
**Machine schemas:** `specification-guide/schemas/`  
**Standing:** normative candidate; exact standing is assigned only by verifier receipts

This file is the stable root entry point for APS syntax. It is intentionally concise. The normative explanations, formal calculus, schemas, profiles, and examples live in the mdBook source and machine-readable surfaces named below.

## 1. Core object

An APS work order is a bounded declaration that connects admitted intent to a falsifiable target consequence. Its minimum semantic form is:

```text
WorkOrder =
  <identity,
   release,
   admitted_source,
   target,
   scope,
   authority,
   obligations,
   exclusions,
   acceptance,
   falsifiers,
   evidence,
   Gall_checkpoints,
   rollback,
   nonclaims>
```

JSON work orders SHALL validate against `specification-guide/schemas/work_order.schema.json`. Receipts SHALL validate against `specification-guide/schemas/receipt.schema.json`. Schema validity is structural admission, not proof of execution.

## 2. Admission and manufacturing

APS separates observation, admission, manufacturing, actuation, and evidence:

```text
O* = admit(O, authority, provenance, relevance, consistency, boundary)
A  = μ(O*)
R  ⊢ A = μ(O*)
```

`O` is the observed corpus. `O*` is the admitted observation. `μ` is the declared manufacturing function. `A` is the bounded artifact or intent. `R` is a receipt that proves only the recorded consequence at the recorded coordinate.

The ggen-aligned control sequence is:

```text
parse
-> route
-> admit | refuse
-> diagnose | repair
-> construct
-> request actuation
-> observe consequence
-> receipt
-> replay | hook
```

Construction is reversible graph-domain work. Consequential filesystem, process, network, deployment, or external-state mutation is DO and SHALL pass through BRCE or another explicitly admitted broker. Zero unreceipted actuation is invariant.

## 3. Normative clauses

BCP 14 words are normative only when uppercase:

- `MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, `SHALL NOT`
- `SHOULD`, `SHOULD NOT`, `RECOMMENDED`
- `MAY`, `OPTIONAL`

A normative clause is incomplete unless it names an object, boundary, verifier, and failure consequence. `MUST` without executable or observable acceptance is prose, not a closed protocol obligation.

## 4. Lifecycle and standing

Lifecycle and evidentiary standing are independent axes.

```text
Lifecycle = Draft | Provisional | InReview | Accepted | Final | Superseded | Refused
```

```text
Standing = PARTIAL_ALIVE | ALIVE | BLOCKED | BUILD_BROKEN
         | UNKNOWN | UNSUPPORTED | REFUSED
```

`Accepted` does not imply `ALIVE`. `ALIVE` does not imply `Final`. Metadata never manufactures standing.

A standing claim SHALL identify the same object, exact source coordinate, command, inputs, outputs, environment when material, failures, evidence, exclusions, and nonclaims.

## 5. Scope and authority

Every work order SHALL declare:

```text
scope.included
scope.forbidden
authority.selector
authority.implementer
authority.verifier
authority.promoter
```

Where risk requires separation, proposer, implementer, verifier, promoter, and actuator SHALL be distinct roles or independently enforced capabilities. Tool discovery, model capability, repository access, and adjacency do not grant business authority.

## 6. Acceptance and falsification

Acceptance is an ordered set of executable observations:

```text
Acceptance = [<id, kind, command, expected> ...]
```

Kinds may include:

```text
unit -> integration -> e2e -> chaos -> stress -> benchmark -> verifier-report
```

A skipped rung is not a passed rung. The required ladder is selected by the claim boundary.

Each material claim SHALL expose a same-object falsifier:

```text
Falsifier = <id, same_object=true, observation, expected_refusal?>
```

Adjacent success is not corroboration. Adjacent failure is not refutation.

## 7. Evidence coordinate

Evidence is a tuple rather than an adjective:

```text
κ = <source, revision, tree, toolchain, target, features,
     environment, command, inputDigest, outputDigest, logicalTime>
```

Fields MAY be omitted only when the governing profile declares them immaterial. Exact-head promotion requires the receipt subject and required checks to refer to the candidate head being promoted.

## 8. Typed refusal

A refusal is a state-preserving protocol result:

```text
Refusal =
  <code, object, law, observed, expected,
   state_before, state_after, repair, evidence>
```

For a refused mutation, `state_after` SHALL equal `state_before`. `UNKNOWN`, `UNSUPPORTED`, `BLOCKED`, and `REFUSED` are not interchangeable.

Replay refusal precedence is deterministic. The ggen profile checks verified duplicate identity before chain-position error, so an out-of-order duplicate returns `DuplicateReplay` while preserving verifier state.

## 9. Gall checkpoint projection

APS owns the declaration boundary. Gall owns checkpoint execution and observed standing. A Gall projection is a deterministic dependency-closed DAG:

```text
Checkpoint =
  <id, claim, predecessors, MUST, MUST_NOT,
   allowed_paths, forbidden_paths, out_of_scope,
   acceptance, evidence, roles, falsifier>
```

Duplicate identifiers, cycles, orphan dependencies, unsafe paths, authority disagreement, and missing acceptance are typed refusals. An empty predecessor set is represented as an empty set.

## 10. Building blocks and enterprise architecture

The ggen profile defines one canonical building-block kernel. Architecture Building Blocks state required capability and constraint. Solution Building Blocks state concrete realization. GBBs, bblocks, packs, and provider profiles compose over one authority graph with deterministic identity and typed conflict refusal.

Enterprise Architecture as Strategy preserves the four Ross–Weill–Robertson operating models and four original maturity stages. `Evidence-Bearing Self-Governance` is an explicit ggen Stage 5 extension. It requires all 21 declared dimensions and all 63 positive, negative, and replay obligations at one exact coordinate.

## 11. Serialization and projections

APS may be serialized as JSON, TOML, YAML, RDF, Markdown frontmatter, or another declared carrier. Round trips SHALL preserve semantically material fields. Lossy output is a bounded projection, not replacement authority.

BPMN, Gantt, C4, ArchiMate, Jira, GitHub Issues, SAFe, POWL, PDDL, and generated code are projections or downstream bindings unless explicitly admitted as authority. Generated outputs SHALL NOT be hand-edited to simulate conformance.
