# Case Studies and Applied Analysis

The cases are analytical counterexamples, not testimonials. Each shows how the same APS laws behave under software, public-sector, privacy, and regulated-release constraints. The object is to expose where ordinary workflow labels would conceal authority or evidence gaps.

## Formal lens

```text
case result = law applied to same-object evidence under domain boundary
```

## Case Studies, Lessons Learned, and Practical Examples

Demonstrates APS through bounded scenarios.

### AI-generated Rust subsystem

**Requirement APS-12-01.** The implementation SHALL represent **ai-generated rust subsystem** as an explicit protocol concern with a stable identifier, authority source, evidence expectation, and failure consequence. It SHALL NOT leave the concern solely in narrative convention or infer it from a tracker status.

**Operational test.** A verifier MUST be able to locate the representation, resolve its dependencies, and produce one of the canonical standing outcomes. Missing representation yields `AI_GENERATED_RUST_SUBSYSTEM_MISSING`; an unavailable checking capability yields `UNSUPPORTED`; contradictory evidence yields a typed refusal rather than a softened success.

**Falsifier.** Conformance is refuted when a same-coordinate candidate can omit or contradict ai-generated rust subsystem while still receiving the standing or lifecycle promotion that the concern was intended to guard.

### Case study 1: AI-generated Rust authority subsystem

An AI agent reported that it had sealed a production certificate type. The repository contained the new type and passing tests, but AST reconciliation found a public `from_raw` constructor in a legacy module. APS classified the work as `PARTIALLY_IMPLEMENTED_BUT_REPORTED_COMPLETE`. A compile-fail client and a constructor-bypass mutant were added. The implementation earned standing only after the legacy constructor was removed and the designated oracle rejected external construction.

### Case study 2: Municipal benefits workflow

A city described eligibility, appeal, privacy, and disbursement laws in an admitted model. The generated workflow separated recommendation from payment authority. During adversarial review, a consequence mutant removed the appeal notification while retaining the eligibility decision. The intended consequence oracle detected that the decision receipt existed without the required notice event. The release was blocked before deployment.

### Case study 3: Privacy-preserving resource coalition

Several nonprofits coordinated transportation and appointment capacity without sharing unrestricted client records. Each participant emitted a bounded projection containing availability, geography, accessibility constraints, and a purpose-limited pseudonymous identifier. APS receipts bound the projection policy and detected a generated adapter that exposed a raw phone number field.

### Case study 4: Regulated release correction

A production release passed its repository test suite but failed package reality verification because the verified policy file was excluded from the package. APS assigned `PACKAGE_MISMATCH`, prevented promotion, and produced an exact repair ticket identifying the missing package include rule.

### Chapter-level minimum conformance

A conforming implementation of this section SHALL make every listed concern machine-readable, SHALL bind evidence to the exact subject coordinate, SHALL preserve the accepted baseline on refusal, and SHALL emit a receipt for successful promotion. The standing ceiling is **PARTIAL_ALIVE | ALIVE | BLOCKED | BUILD_BROKEN | UNKNOWN | UNSUPPORTED**; no chapter text authorizes a stronger claim than observed evidence.
